# lhg-sql-perf：权限与性能自检

目标：SQL 执行前，先证明它"不会闯祸"。核心纪律：**先跑脚本（机器），再做评审（人）；blocker 不清零，不许执行**。

## 1. 何时使用

- SQL 写完、执行前 → 跑全流程
- 接手别人的 SQL 要执行 → 先跑脚本再看逻辑
- 线上慢查询告警 → 用第 4 节定位

## 2. 输入与输出

**输入**：待执行的 SQL 文件/代码目录 + 目标方言 + 表的数据量级（万级/百万级/千万级+）。

**输出**：分级报告（blocker/warning/nit）+ 人工评审结论（通过/不通过）。

## 3. 分步方法论

### 第一步：跑确定性审计脚本（必做，零 LLM 成本）

```
python3 <插件目录>/scripts/audit/sql_audit.py --target <目录> --dialect <方言> --format text
```

脚本输出 JSON（含每条发现的文件、行号、规则说明）与人类可读报告。有 blocker 时 exit code 为 2——这是设计，不是 bug。

### 第二步：分级处理

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 执行会出事：缺 WHERE 的 UPDATE/DELETE、DROP/TRUNCATE、SQL 拼接注入、硬编码凭证 | 必须修，不修不许执行 |
| warning | 大概率是坑：SELECT *、全表扫描、前导 LIKE、N+1、无 LIMIT、方言误用、笛卡尔积 | 修掉或写豁免理由（+数据量级依据） |
| nit | 洁癖项：WHERE 1=1、无列名 INSERT、ORDER BY 序数 | 顺手修 |

分级是死的，判断是活的：小表（万级以下）的全表扫描 warning 可以豁免，但要在报告写清"表 X 约 8000 行，全表扫描可接受"。

### 第三步：人工评审（脚本覆盖不到的）

- [ ] **口径正确**：时间范围、状态枚举值与业务问题一致（如"已支付"对应 `status='paid'` 而不是 `'payed'`）
- [ ] **关联正确**：JOIN 条件是业务上的正确关联；多表时确认不是笛卡尔积
- [ ] **无编造**：表名/字段名与表结构卡一致
- [ ] **权限最小**：取数用只读账号；UPDATE/DELETE 确认账号有写权限且是预期内的
- [ ] **先验证后执行**：UPDATE/DELETE 先跑对应 SELECT 看影响行数；INSERT 先确认目标表

### 第四步：慢查询定位（出问题时）

1. 先看审计脚本的 PERF 类 warning，大概率命中其一。
2. 让用户在库上跑 `EXPLAIN <SQL>`，看 type 列：`ALL`=全表扫描，`index`=全索引扫描，`range`/`ref` 才算正常。
3. 常见病因对照：无 WHERE（加条件）、前导 LIKE（改全文索引）、N+1（改 IN/JOIN）、无 LIMIT（加分页）。
4. **本插件不直连生产库**：EXPLAIN 和执行都由用户在自己的环境跑，报告里只给"去跑 EXPLAIN 看 type 列"这样的指导。

### 第五步：输出报告

```markdown
# SQL 自查报告：<需求>（日期）
## 结论：通过 / 不通过
## blocker（n）：已修 n，剩余 n
## warning（n）：已修 n，豁免 n（理由+数据量级）
## nit（n）
## 人工评审：口径/关联/权限 x/y 通过
## 执行建议：只读账号执行 / 先 SELECT 验证 / 分批执行
```

## 4. 权限清单（取数账号三问）

1. 这个账号是只读吗？（取数场景默认只读，是 → 继续）
2. 需要写操作吗？（UPDATE/DELETE/INSERT → 确认是业务必需，且先 SELECT 验证）
3. 密码在哪？（硬编码在代码里 → blocker，先改环境变量）

### 执行前最终检查清单（打印出来贴显示器边上）

**读操作（SELECT）**：

- [ ] 口径：时间范围、状态值与业务问题逐字对过
- [ ] 表名/字段名与表结构卡一致，无编造
- [ ] 无 SELECT *（COUNT(*) 除外）
- [ ] 有 WHERE 或确认全量是业务所需；大表先看 EXPLAIN
- [ ] 有 LIMIT（先 100 验证），或走分页/流式
- [ ] 方言检查通过（`--dialect` 与目标库一致）

**写操作（UPDATE/DELETE/INSERT）**：

- [ ] 先跑了对应的 SELECT，影响行数符合预期（截图或记录行数）
- [ ] WHERE 条件逐字核对，无"应该对"的条件
- [ ] 执行账号有写权限，且是预期内的账号
- [ ] 有回滚方案（备份表/事务/可重跑的 INSERT）
- [ ] 执行时间避开业务高峰（写操作尤其注意）

**通用**：

- [ ] 审计脚本 blocker 清零，warning 有书面处理
- [ ] 报告结论是"通过"，无"大概没问题"

**清单之外再加一条**：执行前深呼吸一次，问自己"如果这条 SQL 跑错了，最坏的结果是什么？"——答不上来就别执行，先去弄明白。

### 评审记录模板（贴报告里）

```markdown
- 口径：通过（时间范围 2026-10-04~2026-10-11，状态 paid，用户已确认）
- 关联：通过（orders JOIN users ON user_id，外键关联）
- 无编造：通过（字段均出自表结构卡 v20261011）
- 权限：通过（只读账号 bi_reader 执行）
```

四项每项一句话，有依据、无黑话。下次复查时照着模板对，10 分钟复核完。

**评审人签字区**：报告末尾加一行"评审人：<名字>，日期：<YYYY-MM-DD>"。有人签字，评审才不是走过场——这是流程设计，不是形式主义。

> 自检的终极标准：这份报告敢不敢拿给 DBA 看？敢，就发布；不敢，就回去把打叉的项补完。

## 5. 反模式

- ❌ 只跑脚本不做人工评审——脚本看不懂"口径错了"
- ❌ "表很小，全表扫描没事"不写进报告——口头豁免等于没豁免
- ❌ 直接在生产库执行未评审的 SQL——先在测试库跑，行数对得上再上生产
- ❌ 为清零改脚本规则——这是作弊，不是自查
- ❌ N+1 "数据量小，先这样"——数据量小正是改掉它的最好时机

## 6. 自检与反馈

**质检门**（报告发布前逐项打勾）：

- [ ] 审计脚本跑过，blocker 清零（`--dialect` 与目标库一致）
- [ ] warning 逐条有处理（修复或书面豁免+数据量级依据）
- [ ] 人工评审四项（口径/关联/无编造/权限）逐项有结论
- [ ] UPDATE/DELETE 附了先行 SELECT 的影响行数
- [ ] 报告结论是"通过"或"不通过"，无"大概没问题"

**标准冒烟用例**：用本仓库 `fixtures/bad` 跑脚本 → blocker>0 且 exit!=0；用 `fixtures/good` 跑 → 零 blocker 且 exit==0；口径评审用"status 枚举值写错"的 SQL → 人工评审必须不通过。

**一键提 issue**：发现流程缺口或误判，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-sql/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。
