# lhg-sql-ask：中文业务问题 → SQL

目标：把用户的一句中文（如"查一下上周卖得最好的 10 个商品"）变成可执行的 SQL。核心纪律：**先澄清口径，再碰键盘**——80% 的"SQL 写错了"其实是"需求没听懂"。

## 1. 何时使用

- 用户用中文描述取数需求 → 跑全流程
- 需求里有模糊词（"最近""最好""活跃"）→ 重点跑第 2 步
- 拿到表结构但不知道从哪下手 → 从第 3 步的"最小验证 SQL"开始

## 2. 输入与输出

**输入**：中文业务问题 + 表结构（建表语句/数据字典）+ 目标方言。

**输出**：取数五要素确认表 + 表结构卡引用 + SQL（验证版 + 最终版）+ 中文解释。

## 3. 分步方法论

### 第一步：取数五要素澄清（不许跳过）

把中文问题拆成五要素，逐项跟用户确认：

| 要素 | 要问清什么 | 示例 |
|---|---|---|
| 取什么 | 字段/指标 | 订单金额、商品名 |
| 从哪取 | 表 | orders、products |
| 什么范围 | 时间/状态条件 | 近 7 天、已支付 |
| 怎么算 | 明细还是聚合 | 求和、计数、TopN |
| 怎么排 | 排序+截断 | 按金额倒序，前 10 |

**模糊词翻译表**（中文业务黑话 → 可执行口径）：

| 用户说的 | 必须追问 | 落到 SQL |
|---|---|---|
| 最近/上周 | 含不含今天？自然周还是近 7 天？ | `created_at >= '2026-10-04'` |
| 卖得最好 | 按金额还是按件数？ | `ORDER BY SUM(amount) DESC` vs `ORDER BY COUNT(*) DESC` |
| 活跃用户 | 下单算活跃还是登录算？ | 口径定下来再写 |
| 全部 | 真的全量还是"先看一眼"？ | 先 `LIMIT 100` 验证 |

**铁律**：表名、字段名不许编。用户没给表结构 → 用 `/lhg-sql:sql-schema` 先要到表结构，再回来。

### 第二步：表结构理解

1. 画关联：这次取数涉及几张表？JOIN 条件是什么？（外键优先，业务关联次之）
2. 认口径字段：状态字段有哪些枚举值？时间字段是创建时间还是更新时间？
3. 估数据量：表大概多少行？百万级以上 → 第 4 步性能检查从严。
4. 标"待确认"：注释缺失、含义模糊的字段标出来问，不猜。

### 第三步：SQL 生成三步法

**第 1 步：最小验证 SQL**（先证明"我找对表和字段了"）：

```sql
SELECT id, amount, created_at
FROM orders
LIMIT 10;
```

**第 2 步：加条件**（一次加一个，口径逐项落地）：

```sql
SELECT id, amount, created_at
FROM orders
WHERE status = 'paid'
  AND created_at >= '2026-10-04'
LIMIT 10;
```

**第 3 步：成型**（聚合/关联/排序/截断）：

```sql
SELECT p.name, SUM(o.amount) AS total_amount
FROM orders o
JOIN products p ON p.id = o.product_id
WHERE o.status = 'paid'
  AND o.created_at >= '2026-10-04'
GROUP BY p.name
ORDER BY total_amount DESC
LIMIT 10;
```

### 第四步：写给小白的中文解释

每段 SQL 配一句话："这段查的是近 7 天已支付订单，按商品汇总金额，取前 10 名。"让用户能看懂、敢执行、会改条件。

## 4. 反模式

- ❌ 不问口径直接写 SQL——"上周"有三种理解，你猜中的概率是三分之一
- ❌ 凭表名猜字段——`status` 有 5 种可能的含义，猜错就是错数据
- ❌ 一步写出 50 行复杂 SQL——拆三步，每步都可验证
- ❌ SELECT * "先都查出来再说"——下游一多，全表扫描的锅就是你的
- ❌ 生成 UPDATE/DELETE 不带 WHERE——审计脚本会判 blocker，先 SELECT 验证影响行数

## 5. 自检与反馈

**质检门**（SQL 交付前逐项打勾）：

- [ ] 取数五要素每项都有书面确认，无"我以为"
- [ ] 表名/字段名与表结构卡一致，无编造（跑一遍审计脚本 SQL-QLT 类规则）
- [ ] 无 SELECT *；UPDATE/DELETE 带 WHERE 且先 SELECT 验证过影响行数
- [ ] 日期/状态口径有明确值（如 `'2026-10-04'`、`'paid'`），无"最近"这类模糊词残留
- [ ] 中文解释已配，用户能复述"这段 SQL 查的是什么"

**标准冒烟用例**：用"查近 7 天销售额 Top10 商品"走全流程 → 五要素确认表完整、SQL 三步产出、方言检查通过；再给一个"查一下活跃用户"（无口径）→ 第一步必须追问"活跃的定义"，不许直接写 SQL。

**一键提 issue**：发现流程缺口或误判，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-sql/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。

## 6. 取数需求模板（发给用户照着填）

```markdown
### 取数需求
- 一句话：<如：查近 7 天销售额 Top10 商品>
- 取什么字段/指标：<
- 涉及的表：<
- 时间范围：<是否含今天>
- 状态/条件：<
- 明细还是聚合：<
- 排序与截断：<
- 目标库方言：<MySQL/PostgreSQL/SQLite>
- 表结构：<粘贴建表语句或数据字典>
```

用户填完这张表，五要素澄清就完成了一半。剩下的一半是追问模糊词——模板减少遗漏，追问保证准确。

**模板使用提示**：第一次用的用户可能不知道"目标库方言"填什么，直接问他"数据在什么数据库里（MySQL/PG/SQLite）"；表结构拿不到时先按表名推进澄清，SQL 生成前必须补齐。

## 7. 口径沉淀（做一次，省十次）

- 每次澄清完的口径（如"活跃=近30天有下单"）记下来，下次同类需求直接引用。
- 口径变更时更新记录并注明日期，旧 SQL 不追溯，只保证新取数用新口径。
- 团队共用：口径文档放仓库 `docs/metrics.md`，新人取数先看它。
